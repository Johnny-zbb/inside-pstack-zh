关于 pstack 与这份报告

pstack 是 Lauren Tan（poteto）在 Cursor 工作时构建的一套代理技能，她至今每天都在用。她是 React Compiler 核心团队成员，曾在 Meta 和 Netflix 任职。原文称，SpaceX 收购 Cursor 后，她自 2026 年 8 月起在 SpaceXAI 开发 Grok Bot。

技能包围绕路由技能 /poteto-mode 组织。它为任务选择操作流程，再按步骤调用其他技能。

README 写明了目标：“少写代码，提高质量。”本报告逐一阅读技能包中的文件，解释各项技能的结构、设计原因，以及值得复用的做法。

公开版本位于 cursor/plugins/pstack，采用 MIT 许可，安装命令为 /add-plugin pstack。#156、#329 和 #414 将 Cursor 内部技能目录的修改移入公开仓库，因此公开版本是内部版本经过整理后的镜像。她的个人 GitHub 没有独立的 pstack 仓库，但保留了前身：noodle、brainmaxxing 和 how。

每个技能都是一个目录，包含 SKILL.md，由 YAML 元数据头和 Markdown 正文组成。目录还可包含 references/、scripts/ 或 playbooks/。这采用开放的 Agent Skills 格式，Claude Code 也能读取。为子代理按角色指定模型、自定义模式、/loop 和云端代理等编排功能，则依赖 Cursor。

先看结构图和文件结构，了解技能包如何组织。技能与操作流程索引可供随时查阅，点击任意条目即可展开。最后四节介绍她的使用习惯、公开理念、本文评价，以及构建自己技能包时可以借鉴的做法。

译自 Inside pstack。版本、数字与评价保留原报告 2026 年 10 月 14 日的口径。中文表达依照 zh-tech-writing 整理。

01整体结构

一个路由、多套流程和少量多代理工作流

你给出目标和明确的验收条件，路由据此选择操作流程。流程按步骤调用工作流技能，再分派给使用相应角色模型的子代理。提交拉取请求（Pull Request，PR）前，所有结果都必须在真实应用中得到验证。

操作流程中的子代理以 poteto-agent 身份运行，执行前先加载 poteto-mode。工作流技能各自设置 subagent_type 和模型，让审查者来自不同模型家族。

02技能的文件结构

文件怎样组织

pstack 的技能遵守几项严格约定。这些约定承载了大部分设计。构建自己的技能包时，可以先借鉴它们。

# principle-encode-lessons-in-structure 的 SKILL.md 全文译文 --- name: principle-encode-lessons-in-structure 1 description: "当同一指令需要写第二遍， 2 或同类纠正反复出现时适用。将规则写成 lint、 元数据标志、运行时检查或脚本，减少文字指令。" disable-model-invocation: true 3 --- # 把经验变成结构约束 经验需要判断、无法编码时，应突出说明指令， 4 并补充一个失败案例。 推论：问题能通过结构修复时，就只做结构修复。 重复指令只是问题的表现。
1

名称同时是目录名和引用标识。其他技能用“encode-lessons-in-structure 原则技能”来引用它，不复制正文。

2

description 同时说明触发条件和规则。先写“适用于……”，再写规则。许多原则的大部分内容都在 description 中，路由索引可以直接引用。

3

54 个技能中，有 53 个设置了 disable-model-invocation: true。提示词里出现相关词语，不会自动加载技能。只有显式调用，或 poteto-mode 的步骤要求时，技能才会运行。唯一的例外是 setup-pstack。

4

正文只补充 description 放不下的内容。这个文件的英文正文仅 34 词。提交历史多次删去新模型已不需要的指令：#329 删除 633 行，#419 又删除“Opus 5.5 不需要的 19 条指令”，#538 删除 736 行。

A

SKILL.md 负责编排，references/ 保存子代理需要阅读的材料。SKILL.md 指定何时启动哪类子代理，以及使用哪个角色模型。参考文件按接收者命名，如 explorer-prompt、runner-prompt 和 judgment-reviewer；开头用一句话提示编排者如何分发。

B

每个子代理都有固定的输出约定，包括准确的标题和逐项字段，便于下一阶段读取。调查者只收集证据。一个汇总者统一处理发现，并抽查引用。

C

必须写出不确定之处。无结果的搜索、跳过的来源及原因、尚未查清的问题，都是必填内容。epistemics 文件写道：“如果完全没提信息缺口，就值得怀疑。”

流程以职责开头，以回复要求结尾

每套流程先用一行加粗文字说明职责，例如：“你负责保证契约。可以改变结构，必须保持行为。”随后列出编号步骤，最后用 Reply: 明确最终回复必须包含什么。

先将步骤写入待办清单

poteto-mode 将所选流程的步骤原样复制到待办清单。architect、arena、swarm 和 figure-it-out 为每个阶段各建一项待办。跳过的步骤仍保留，并标记 skip: <reason>。

按角色命名模型

技能请求“how explorer”“arena runners”等角色，再由 pstack-models.mdc 映射到模型标识。每个技能也规定了标识不可用时的处理方式：回退到该家族的默认模型，说明回退情况，然后继续。

规则使用稳定标识

unslop 的规则都有编号。删除规则后保留编号空缺，让“unslop 第 14 条”始终指向同一条规则。原则名和技能名也起同样作用。

用脚本执行重要规则

文档要求“运行 X”时，X 就是确定性的工具。check-plan.mjs 检查计划，watch-pr 返回带类型的判定，log.sh 写入格式正确的制表符分隔值（TSV）记录。脚本负责检查，文字指令便可保持简短。

标注外部输入不可信

会话记录、Bugbot 评论、审查结果和 webhook 请求体，都标记为“不可信数据”。回复文字不拼接进 shell 命令。会话记录的读取范围限定为当前工作区。

04操作流程

/poteto-mode 中的 23 套流程

操作流程（playbook）存放在 poteto-mode/playbooks/ 下，是没有斜杠命令的 Markdown 文件。路由根据任务匹配流程，你也可以直接说“看护这个 PR”“合并这组 PR”或“自动处理这个队列”。条目显示原文词数，便于估计加载成本。

05原则

24 条原则，每条一个文件

她称这些原则“可能是 pstack 最持久的部分之一”，并预期模型进步后，多数其他技能会压缩成简短的原则或工作流。她在 10 月 14 日的 X 帖子中说，许多原则来自年初以来纠正代理的会话。当天的 #633 将其中四条从具体规则改写为背后的理由，下方卡片采用新表述。poteto-mode 内嵌原则索引，每条都有适用条件和规则。应用前，代理必须打开对应文件；回复中必须说清哪条原则改变了哪个决策。日常使用时，你只需用名称引导，例如：“应用 prove-it-works，给我看真实输出。”

06模型与子代理

为每个角色选择合适的模型

pstack 为不同工作分配不同模型。速度快的代码模型负责阅读和机械修改，判断能力较强的模型负责写作、评判和最难的改动。审查始终搭配不同模型家族，因为“不同模型得出一致意见，是很有价值的信号”。

poteto-mode 的子代理规则

  • 每次启动都指定模型，在后台使用 agent 模式运行。只读模式会移除模型上下文协议（Model Context Protocol，MCP）工具权限。用文件路径传递上下文，避免复制整段材料。
  • 按任务调整模型配置。0.15.24 新增 以角色指定的模型为起点，只调整推理强度和速度。最难的任务提高一档，判断工作降低一档，常规工作降低两档或更多。仅在持续集成（Continuous Integration，CI）或主干检查失败、有人正被阻塞时使用快速模式。验证仍使用 swarm 指定的模型。模型家族保持不变，让评审组保留差异。
  • 默认启动新的子代理。每轮修复、重试或队列中的下一项任务，都向新代理提供整合后的任务说明。只有旧代理持有难以迁移的状态时才恢复它，例如检出目录、未提交改动或正在运行的开发服务器。“连续中断再恢复，会悄悄丢失指令。”
  • 主代理对结果负责。亲自审查差异并撰写说明。
  • 必须分离实现与审查。存在多种合理设计的功能，必须经过 arena；“懒惰协议”也不能免除这一步。
  • 评审者来自另一模型家族。arena 的评委、show-me-your-work 的记录审查者，都必须与作者使用不同家族的模型。

07脚本

将规则写成可执行代码

poteto-mode/scripts/ 下约有 7,000 行 Bun 和 TypeScript 代码、约 63 个测试，并执行严格类型检查。每个脚本都替代一条代理可能忘记的规则。技能包也在对自身应用 encode-lessons-in-structure 和 build-the-lever。

脚本调用者执行的规则
check-plan.mjsmulti-phase-plan，第 6 步检查计划文件：不能出现长破折号、弯引号或句中冒号；固定结构必须按顺序出现；验证语句必须逐字一致；恰好 10 条并行执行线，每条都有截图和通过条件；性能项包含 Metric、Probe、Baseline 和 Rule。任意问题都会使退出码变为 1。
watch-prbabysit、shipping轮询 GitHub，返回带类型的判定与退出码：READY/COMPLETE 为 0，冲突为 2，待处理审查讨论为 3，检查失败为 4，合并关卡为 6，查询失败为 7，TIMEOUT 为 5。脚本统计 Bugbot 轮次，从第 3 轮开始倾向于驳回低价值意见。代码审查关卡等待所有者批准时，会识别为该关卡，避免一直等待人工处理。
orchorchestrate基于文件记账，“输入一条命令，输出一行结果”。内容包括 units.tsv、按 PR 与头部提交 SHA 索引的验证账本、收件箱、关卡、可推进的前沿和常驻指令。新 SHA 会使旧判定失效。脚本自身不启动代理。基于进程标识的锁可在崩溃后恢复。自 0.15.24 起，通过 gh 或 Origin 读取 PR 的基础分支依赖，已经不再需要 Graphite。
worktree-audit.shworktree-cleanup只读执行。路径来自 git worktree list。优先从 Origin 读取 PR 状态，否则使用 gh。工作树分为 hold-wip、hold-open-pr、verify-recent-chat、safe 和 review。“分类是建议，不代表删除许可。”
log.shshow-me-your-work追加带时间戳的 TSV 行，移除制表符和换行，并为以 =、+、- 或 @ 开头的单元格加前缀，防止日志注入电子表格公式。
bootstrap.tswatch-pr, orch安装脚本唯一的依赖。用 package.json 与 bun.lock 的哈希识别依赖状态，重复运行不会再次安装。技能无需额外提醒“先运行 npm install”。
08她怎样使用

用简短提示词写清验收条件

十页指南 docs/guide/ 和 poteto-help/references/prompting.md 介绍了她的提示方式。原文提示词用小写、口语表达，只写目标和完成标准，把方法留给代理。

提示词的五项内容

  • 目标。
  • 明确的验收条件。“改好一点”和“做一个小时”都无法判定通过或失败。
  • 你希望看到的证据。
  • 已知信息，例如任务 ID 和失败的测试样本。
  • 实际约束，例如“先复现”“暂时别改代码”“行为完全不变”“连缺陷也保留”和“逐字节一致”。

不要在提示词里列出技能调用顺序，手写顺序可能打乱或漏掉流程步骤。也不要先给出原因猜测，它会将搜索范围限制到你指出的位置。

将五项内容写进一条提示词

/poteto-mode 昨天部署后，CSV 导出开始丢失最后一行。失败任务 ID 是 4812。先复现，再修复。验收条件：包含 60,000 行的测试样本逐行导出。给我看修改前后的行数。

后续指令保持简短

/poteto-mode 执行。 继续。 /poteto-mode 新任务：查清缓存项为什么在退出登录后仍保留。暂时不要改代码。

夜间执行的约定

/poteto-mode 我要睡了。[1] 从 <base> 创建独立工作树，把所有调用方迁移到新解析器。[2] 验收条件：旧调用方数量为零，所有解析器样本通过，旧 API 已删除。[3] 保留决策日志，提交前不用问我。[4] /loop 直到完成。几小时后仍确实受阻时，停止并说明原因。[5]

[1] 本次会话的授权，减少执行中的询问。[2] 隔离环境。[3] 每轮都能执行的验收检查。[4] 可复核的记录与提前给出的提交许可。[5] 唤醒机制与退出条件，避免代理花 8 小时不断重新解释目标。

先建立信任，再循环执行

  • 你手动做过一次任务，或观察过代理完成。
  • 代理拥有所需工具和信号，例如验证技能、性能分析器和日志。
  • 每个阶段都能证明结果，发现问题时能停止后续执行。
  • 你已阅读会话记录，并将重复失败转成工具、技能或检查。

满足这四点前，应当在旁观察运行。第二天早上运行 /show-me-your-work 介绍昨晚完成的工作，先读另一模型审查的“需要关注”部分。

按问题选择设计工具

  • 对已经完成的小改动没把握 → /interrogate。
  • 改动跨越函数边界 → /architect，它会运行 arena。
  • 命名、格式或算法等独立决策 → /arena。
  • 需要覆盖矩阵 → /swarm。
  • 可以运行代码回答的问题 → 做原型。
  • 存在争议、难以撤回的设计 → 先 architect，再 interrogate。
  • 涉及多个 PR 的工作 → 最后再写计划。

“大多数改动不需要这些流程。”她还说，/interrogate 应当审查实际差异。审查抽象计划，容易凭空制造根本不会出现的风险和边界情况。

一句话调整方向

我要求先复现，还没要求修复。 应用 prove-it-works，给我看实际输出。 使用 subtract-before-you-add，先删掉过时的适配器。 /teach 解释为什么这样实现，以及队列方案的取舍。 /unslop 检查这段文字，去掉长破折号。 /bro

她列出的常见问题

在提示词里罗列技能。完成条件含糊。先说原因猜测。直接采用第一个设计。润色抽象计划。多个代理同时修改同一个工作树。还没建立信任就循环执行。相信未经验证的数字。反复手动纠正同类错误。接受每条审查意见。仅凭构建通过就宣告成功。

她认为最值得投入的地方

指南第 1 页指出，验证技能的回报最高。能自查的代理会持续工作，直到检查通过；无法自查的代理，每次都把结果交回给你。每个仓库运行一次 /create-verification-skill，然后在提示词中写：用 /verify-<app> 验证改动，并提供视频和截图作为证据。

09她的理念

她如何描述这些理念

以下引文译自她在 2026 年 3 月至 10 月的 X 帖子和长文。阅读生产力数字时，也应考虑她在推广 Cursor 和 Grok Bot。

“代理编排要先深入解决问题。……简单地增加并行，只会让低质量代码写得更快。”

《我如何使用 Cursor》，2026 年 5 月 25 日

“每次介入并纠正代理时，都应该思考如何彻底消除这个问题。按价值排序：1. 用更好的架构或数据结构，从根本上消除问题；2. 写成 lint 规则或测试，让 CI 捕获；3. 写成技能或规则；4. 靠人工审查发现问题，这条路难以为继。”

“模型越来越聪明后，我预期大部分 pstack 技能会压缩成简短的原则或通用步骤，有些技能也就可以删除。”

X，2026 年 10 月 14 日

主要观点

  • 先建立信任，再增加并行。先让一个代理深入工作，直到结果可以验证，再同时运行多个代理。并行使用自己还不信任的代理，会浪费大量 token。
  • 验证是核心产出。指南第 1 篇题为《验证就够了》。她认为验证技能更像关键基础设施。
  • 代码库就是记忆。代理会模仿现有代码，因此应从结构上消除错误路径。她说：“我认为代码库是最终极的记忆形式。”
  • 像管理者一样监督。《可信的循环》借鉴安迪·格鲁夫的《高产出管理》：先亲自做一遍，把工具交给代理，每个阶段都要求证据，并阅读会话记录。
  • 让模型做各自擅长的工作。她认为 Opus 擅长管理代理，可以用它编排其他模型。

这些数字有多可信

她曾说“本月交付近 1,000 个 PR”（7 月 29 日）、“两天合并并交付 221 个 PR”（8 月 7 日），以及“上个月交付 2,500 个 PR”（9 月 21 日演讲）。指南则写约每月 2,000 个。这些数字均为自述，未经审计，口径也不一致。她向 Matt Pocock 解释，这显然不等于 2,500 个功能，并承认完全自动执行会消耗很多 token。

她在 10 月 11 日还质疑“可维护性和整洁代码仍然重要”的说法，把好代码定义为正确、无缺陷、速度快、运行成本低。这与 pstack 自身的 minimize-reader-load 原则存在张力。本文的一种解释是：她如今更看重下一位代理的阅读体验，因此代码应让它无法走上错误路径。

10如何评价

本文的评价

以下评价来自对全部 54 个技能、脚本和历史的阅读。这些思路可以迁移到其他工具，但完整编排成本较高，也有部分功能依赖 Cursor。

值得借鉴
  • 每一步都要求证据。结论标记为实测、推断或猜测；blast-radius 的五级证据、why 的置信分级，以及“信息缺口不能算通过”，都给审查者留下可检查的依据。
  • 作者与评审者分离。Comment Sicko、跨家族评委、每个 PR 合并前的独立验证，以及由另一模型复核决策记录，都遵守这一点。
  • 把规则写进结构。/correct 的修复顺序、check-plan 和 watch-pr 脚本，以及“规则 → 执行工具”表，把关键要求转成代码。
  • 技能不断缩短。每次删减都检查行为是否保留。原则文件的英文正文可以只有 34 词。她以“已无内容可删”作为技能完成的标准。
  • 加载行为可预期。显式调用加上一个路由，让上下文保持较小。
成本与限制
  • token 成本。多模型评审、每个 PR 的 10 条并行执行线和跨模型复核，都会增加消耗。The Neuron 引用的一名测试者称，不用 pstack 约需 30 分钟，使用后约需 1 小时，但后者发现了 3 条错误断言。
  • 小任务可能承担过多流程。Flavio Copes 认为，有些任务不需要这么多手续。路由允许用 skip: <reason> 跳过，也承认多数改动不需要这些流程，但整体仍偏重。
  • 文字只能指导。真正强制执行要求的是脚本。其余部分仍依赖模型遵守指令，因此她持续把规则移进代码。
  • 个人工作风格。技能包包含她的习惯、模型配置（Opus 5.5 + Grok 4.7）和工具组合（GitHub 或 Origin、Bugbot；10 月移除 Graphite）。她提供 /automate-me，让你在此基础上构建自己的模式。
  • 生产力数字来自自述。她与 Cursor 和 Grok Bot 也存在商业利益关系。
迁移到 Claude Code

SKILL.md 格式可以直接迁移，编排逻辑需要改写。社区移植版 michael-denyer/pstack-claude（原文记录约 2,000 星）支持 Claude Code、Codex 等；backnotprop/pstack（原文记录约 1,900 星）支持 Claude、Codex 和 pi。两者均在原文所述的 10 月 14 日更新。一篇评测指出，移植版的审查差异只来自独立上下文，未必来自不同模型家族。这是移植时主要的能力损失。

11构建自己的技能包

建议按这个顺序借鉴

以下顺序结合她的优先级，以及各技能对其他部分的依赖，按投入回报排列。

  1. 为每个应用编写可验证行为的脚本。包含 Launch、Doctor、Drive、Evidence 和 Cleanup 五节，以及每项功能一个文件的功能图。她将此列为指南中最值得投入的部分，整套技能包的“已验证”标准都依赖它。

  2. 每次回复都要求证据。借鉴 poteto-mode：每项结论标注实测、推断或猜测，自己能运行的检查自己完成，并原样提供先失败、后通过的输出。

  3. 将作者与评审者分成独立代理。可从专门删注释的审查者，以及看不到模型名称的评委开始。有其他模型可用时，就使用不同模型。

  4. 编写一个路由和几套小流程。每套流程包含职责、复制进待办清单的编号步骤，以及 Reply: 输出要求。自己的 -mode 可以从调查、缺陷修复和功能开发三套流程开始。

  5. 把重复纠正变成结构约束。按 /correct 的顺序，先改架构，再用类型或能指出修复方法的 lint，然后是测试，最后是文档。在 CLAUDE.md 中维护“规则 → 执行工具”表。没有执行约束的规则，仍算问题可能重现。

  6. 默认只允许显式调用，把规则写在 description 中。设置 disable-model-invocation: true，并用“适用于……”加规则的格式，让索引可以引用。

  7. 用 SKILL.md 编排，把子代理提示词放进 references/。给每个子代理规定下一阶段可以读取的固定输出。执行者收集证据，一个评审者统一下结论。

  8. 为无人值守执行保留决策记录。使用只能追加、带证据列的 TSV 文件。结束时与会话记录核对，再交给另一模型复核。

  9. 删减并评估。删掉当前模型无需提醒也能遵守的指令。盲测技能修改：使用自然任务提示词、去标识的目录，并根据会话记录评分。

  10. 从更小的范围开始。她建议，同类失败第二次出现时，再补一个技能或检查。pstack 从 brainmaxxing、noodle 和 how 逐步发展，每次只把重复失败转成技能。

12历史与来源

发展过程

日期取自 cursor/plugins 提交历史和她的帖子。共有 129 次提交涉及 pstack/，其中 123 次由她提交。

  1. 2026 年 2 月至 4 月

    个人 GitHub 中出现前身：brainmaxxing 包含 encode-lessons-in-structure、prove-it-works 等原则和 reflect；noodle 用技能编排代理，已有 unslop 和 adversarial-review；还有 how。她在 3 月底从 Meta 加入 Cursor。

  2. 5 月 22 日至 25 日

    cursor/plugins 合入“Add pstack plugin”，共 74 个文件、18 条原则。5 月 25 日发布《我如何使用 Cursor》。

  3. 5 月至 6 月

    版本从 0.2 演进到 0.9。新增多模型 /interrogate、按角色配置模型的 /setup-pstack，以及 hillclimb 流程。6 月 24 日发布《可信的循环》。

  4. 7 月

    新增 create-verification-skill、maintain-verification-skill 和 swarm。评审组一度默认使用 Fable、Sol 和 Grok 三种模型。

  5. 8 月

    0.13 至 0.14。新增自动执行流程、配合 Comment Sicko 的 /no-comments，以及 /technical-writing、babysit、shipping、orchestrate 和 bro。原文称，SpaceX 收购 Cursor 所属公司后，她在 8 月 17 日入职 SpaceXAI。

  6. 9 月

    0.15.0 删除技能中的长破折号和刻意的文风，新增 attack-the-premise 和 test-behavior-not-implementation。默认模型改为 Opus 5.5 + Grok 4.7。完整指南前两篇及“上个月如何交付 2,500 个 PR”的演讲发布。

  7. 10 月

    新增 /correct、/benchmark-checklist、/poteto-help 和 /ketchup。评审组移除 Sol，默认推理强度从 max 改为 xhigh。她称“pstack 体积缩小了 10%，行为没有损失”。10 月 13 日的 0.15.23 新增 /in-your-own-words。

  8. 10 月 13 日至 14 日

    发布 0.15.24 和 0.15.25。/sharpen 将三份技能草稿合为一项。#613 按任务调整子代理的推理强度与速度，精简 shipping 和两套自动执行流程，为规则补充理由；每个 PR 只运行一次完整 swarm，并移除 Graphite。自动执行流程通过 /ketchup 汇报，#628 又要求用截图、视频和图示解释改动。#633 将 attack-the-premise、fix-root-causes、test-behavior-not-implementation 和 make-operations-idempotent 改写为背后的理由，让代理可以处理未被列举的情况。

她有个人 pstack 仓库吗

原文称没有独立版本，只有 cursor/plugins，以及她用于开发的分支仓库 poteto/plugins。pstack 也列为 Grok Bot 插件。相关公开项目 poteto/verification-skill-example 提供验证技能与功能图的完整示例。原文记录的 X 简介提到在 @SpaceXSI 开发 Grok @Bot，使用 pstack 交付，曾任职 Cursor、Meta 和 Netflix。
